# 原则

这些原则对登记进来的任何一套系统都有效。某一套系统特有的边界写在 `systems/<system>/overview.md`，不要写进本文件。和某一轮需求冲突时，先改需求文档并记一笔决策，不要悄悄破例。

1. 已有数据的默认行为保持不变，除非这一轮的需求写明了怎么处理老数据。
2. 地址、端口、令牌放配置或数据库记录里，不写进代码常量，也不写进迭代文档。
3. 页面上按钮显不显示，不等于接口允不允许调用。不要在没写进需求时，顺手加接口白名单。
4. 改动不得超出该轮 `change-scope.md`。范围不够就先补文档；历史轮次按自己的 `file-map.md` 定位实际文件。
5. 先有验收和用例，再改代码。自动测试至少留下一条能在这条逻辑坏掉时失败的检查。纯文案可以只做手工用例。
6. 沿用该项目已经在用的删除方式。原来是软删除的，不要新加物理删除。
7. 文档用白话。接口名、字段名、文件路径保持代码里的原文。
8. 代码仓库只在 `overview.md` 写绝对路径，迭代目录里不放源码，也不做指向仓库的文件夹快捷方式。默认使用真实仓库，未提交修改只登记基线；只有另一 `implement` 或 `verify` 轮次使用同一仓库时，才允许由框架脚本在根目录 `.worktrees/` 创建临时副本。它不是长期源码目录，收口前必须先把成果同步到真实仓库的显式目标分支并验证，再清理或记录用户确认保留。系统知识库用绝对路径软链接，文件夹名是 `knowledge-base`，指向该系统自己的文档目录，不复制进迭代目录。某一轮没有额外资料时可以不建知识库。
9. 默认只读。用户明确说“开始执行”“开始处理”，或以等价自然语言下达阶段审批、执行当前任务、完成所有任务、开始验收、确认收口等可执行指令时，才允许在该指令范围内写文件；疑问、条件、否定和普通讨论不构成授权。“完成所有任务”不隐含验收或收口，三个范围分别识别。提交、推送、合并、拉取、部署、迁移、服务启动和外部写入仍需单独授权。
10. 每条代码任务写入前执行实现守卫，完成实现后即可勾选；首次进入 `verify` 前统一检查和审核，验收返工只增量审核新任务并按风险重跑受影响项。
11. `verify` 的功能验证范围包含本轮直接功能和一层高概率相邻功能；相邻范围必须有影响依据和停止边界，不做无关的全系统回归。
12. 同一系统可以有多个活动轮次；每个 Agent 会话只绑定一个。`specify`、`plan` 可以并行，`implement`、`verify` 必须使用互不冲突的产品检出路径和独占运行资源。
13. 框架增强默认复用现有文件、阶段和命令。新增强制产物、固定步骤、默认必读正文或全量检查前，必须证明风险收益且不能把成本平摊到所有低风险迭代；日常只读取 `read_next`，测试和复验继续按风险执行并复用未失效证据。
