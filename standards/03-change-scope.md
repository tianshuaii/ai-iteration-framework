# 改动范围

每一轮都要有 `change-scope.md`。没有这份文件，不允许改代码。历史轮次仅通过本轮 `file-map.md` 映射旧文件名。

## 必须写清的三块

1. **这套系统**：写 `systems/` 里登记的系统名。系统里有多个仓库时，逐个写这一轮动不动。
2. **要改的仓库**：写 `overview.md` 里的仓库名和大致文件。是改现有文件，还是新增迁移、新增测试，要分开。路径写该仓库内的相对路径。按 `overview.md` 里的绝对路径打开原来的仓库，不要把源码放进迭代目录。
3. **明确不动的仓库**：这套系统里没点名的仓库，全部写进「不动」。

## 页面位置要扫全

用户只圈出一处时，不能只写那一处。写 `change-scope.md` 之前，把同一页面上会跟着变的位置都列出来，每处写「现在显示什么、改完显示什么」：

- 页头说明、空状态文案
- 筛选项和表头
- 新增、编辑弹窗里的每一项
- 同一功能的结果弹窗、详情、提示（例如连通测试）
- 按钮旁的说明

只在代码里出现、页面上看不到的字段，放进「大致文件」，不要和页面位置混在一节。

## 文件范围怎么圈

- 写入口和它直接带上的调用处，不要把整个 `src/` 圈进来。
- 表结构若多个项目共用，写明迁移只在哪一个项目执行，其他项目只同步模型。
- 页面改动写到具体的 `.tsx`。类型定义若要跟着改，单独列出来。
- 测试文件和被测文件写在一起，标成「补测试」。
- 做的时候发现必须再碰一个文件，先把路径补进这份文档，再改那个文件。

## 和仓库地址的关系

一套系统的代码仓库只记在 `systems/<system>/overview.md`，每条都是绝对路径。通常直接去原仓库看代码、改代码；原仓库有未提交修改时继续使用该路径并登记逐文件基线。只有另一 `implement` 或 `verify` 轮次使用同一仓库时，才能由 `scripts/create-worktree.rb` 在框架根目录 `.worktrees/` 建立临时 Git worktree。迭代目录里不放源码，也不做指向仓库的文件夹快捷方式。收口时先由 `scripts/sync-worktree.rb` 把目标分支拉取到真实仓库并验证包含最终 HEAD，再由 `scripts/cleanup-worktree.rb` 清理临时副本并恢复文档指向。

`overview.md` 和 `iterations/` 是这套系统自己的文件，不要写进仓库，除非那一轮明确要求改仓库文档。
