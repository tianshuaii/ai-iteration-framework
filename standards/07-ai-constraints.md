# AI 开发约束

把一轮迭代交给 AI 时，先看该轮 `status.md` 的 `phase`，再打开 [prompts](../prompts/README.md) 里对应的那一份入口。除了该轮文件夹，还要遵守下面这些。

## 开工先读

1. 框架根目录与该系统目录适用的 `AGENTS.md`
2. 该系统的 `agent/README.md`，按目录、用户点名或活动轮次数量给当前会话绑定一个轮次
3. 所绑定轮次的 `status.md`，只从中取得 `phase`、`current_task`、`work_state`、`updated_at`、`checkpoint` 和 `next_action`
4. 所绑定轮次存在 `file-map.md` 时，先用它定位历史文件；否则使用标准英文文件名
5. `standards/00-principles.md`
6. 该系统的 `overview.md` 和 `knowledge-base/`。所绑定轮次另有 `knowledge-base/` 时也读
7. 所绑定轮次的需求、决策、改动范围、任务清单和验收标准

## 只读范围

为了确认实现与影响，可以只读搜索当前任务相关的调用链、同类实现、测试、配置和 Git 状态。不要把“只能写哪些文件”误解成“只能读取哪些文件”。

## 写入授权与范围

- 用户当前请求没有明确说“开始执行”“开始处理”，也没有用等价自然语言下达阶段审批、执行当前任务、完成所有任务、开始验收或确认收口等可执行指令时，不写任何文件；实现、验收和收口分别按当前原话授权，疑问、条件、否定和普通讨论保持只读。
- `implement` 阶段只写 `current_task` 与 `change-scope.md` 共同允许的产品文件，以及本轮固定状态文件。
- 进入 `implement / ready` 前先把拟使用的产品检出路径、隔离方式和运行资源写入该轮 `workspace.md`；默认使用真实仓库。修改产品文件前再逐文件采集分支、HEAD 和已有 dirty 状态；不得覆盖接管前改动，dirty 本身不触发 worktree。
- 多个活动轮次存在时，只有另一 `implement` 或 `verify` 轮次登记使用同一仓库，当前轮才需要独立产品检出；两个产品活动轮次不得复用同一检出路径或同一个独占运行资源，不能隔离就留在 `plan / blocked` 串行处理。
- 符合同仓库产品阶段并行条件时，只能用根目录 `scripts/create-worktree.rb` 创建到 `.worktrees/`，由本轮 `workspace.md` 记录原路径、临时路径、分支、HEAD 和状态；不得在其他位置手工创建长期遗留副本。收口前显式记录目标分支，并按授权使用 `scripts/sync-worktree.rb` 拉取真实仓库和验证最终 HEAD。
- 开始工作前把 `work_state` 改为 `in_progress`；暂停、阻塞或完成可恢复步骤时同步更新 `updated_at`、`checkpoint` 和 `next_action`。
- 提交、推送、合并、拉取、部署、迁移、外部系统写入和 `knowledge-base` 写入不随普通代码授权自动获得权限。

## 阶段锁

- 新建迭代必须调用 `scripts/create-iteration.rb`，禁止人工创建轮次目录或复制模板；脚本不可用或执行失败时停止写入并报告阻塞，不能绕过 `.iteration-create.lock`。
- `specify` 和 `plan` 完成后保持 blocked，只有用户以“需求审批通过”“计划审批通过”或含义明确的等价自然语言批准，并由 `scripts/record-stage-approval.rb` 分阶段写入 `stage-approvals.md`，才能继续。联合审批原话不跳过阶段能力门禁；普通“继续”“开始处理”“可以”都不能代替审批。“完成所有任务”只扩大实现任务和统一审核的连续执行范围，不包含验收或收口，也不扩大外部变更权限。
- 实现与统一审核通过后进入 `verify / blocked`，等待明确验收授权；验收和 `iteration-test-verification` 通过后仍保持 `verify / blocked`，等待明确收口授权。只有当前原话明确联合授权对应阶段时才连续执行；不得从先前授权、阶段切换或测试通过推断后续权限。
- 需求与计划审批前按 `capabilities.yml` 完成 `grill-me` 或登记的降级访谈及阶段评审；用户对结构化访谈的回答只授权本轮阶段文档。每条产品任务写入前执行 implementation guard；全部任务实现完成后才对本轮整体差异执行一次 `code-review-skill` 或登记的降级审核，并把证据写入 `capability-log.md` 与 `evidence/`。
- MCP 默认只读。Skill、MCP 或总控 `iteration-governor` 都不能替用户审批，也不能扩大到提交、推送、部署、数据库或其他外部写入。
- 需求或计划摘要失效时必须退回对应阶段重新审批；需求重批会重置计划审批。计划审批不等于当前任务执行授权，同回合改代码还要明确要求执行 `T-xx`。
- `specify` 和 `plan` 不许改 `overview.md` 里列出的仓库。
- `implement` 有 `T-xx` 时只实现 `current_task`，产品文件必须同时出现在改动范围和任务条目里；任务完成即可勾选并切换。首次进入验收前执行整轮审核；验收返工只对新任务执行增量审核和受影响检查。
- `verify` 跑计划内自动测试、正式 AC/TC 和受控浅功能回归，并填写测试记录、验收结果和评审清单。浅回归覆盖直接功能和一层高概率相邻功能，必须有纳入理由和停止边界，不得扩张成全系统回归。失败时只允许按验收入口追加返工任务或回退规格，不在验收阶段改产品代码。
- `verify` 收口时，成果提交、合入并推送目标分支后，先取得拉取授权并用 `scripts/sync-worktree.rb` 在真实仓库执行 `git pull --ff-only`，验证目标分支包含 worktree 最终 HEAD；再用 `scripts/cleanup-worktree.rb` 清理根目录 `.worktrees/` 中本轮的干净副本。清理脚本二次验证同步证据，阻断脏目录，不使用强制删除，也不删除成果分支。目录清理后把当前产品路径恢复为 `overview.md` 真实仓库，同时保留临时路径、最终 HEAD 和同步证据。
- `done` 之前不得留下“使用中”或“待清理”的 worktree；只有用户明确确认并记录保留原因时才能保留。`done` 之后才把本轮结论补进该系统知识库。本轮文件夹留着当档案。

## 过程汇报

- 每次过程更新都包含 `已完成：` 和 `下一步：`，不得在命令结果、服务状态或故障说明后直接结束。
- Agent 可以继续时写 `无需你操作：` 并继续执行，不要求用户为了确认普通进展而回复。
- 缺少输入、授权或外部操作时写 `需要你：`，只给一条明确动作；真正受阻时同步更新 `status.md`。
- 回合结束时，用户可见的下一步和 `status.md` 的 `next_action` 必须表达同一动作。

## 允许做的

- 在 `implement` 阶段改当前任务点名的文件
- 把这一轮临时脚本放进该轮 `scripts/`。不要把密码、令牌、内网地址写进脚本
- 发现范围不够时停下来，先补改动范围再继续
- 为这次的分支补最小自动测试
- 首次实现完成后汇总去重检查命令；返工只执行风险策略中受影响的必跑项，并把执行与复用依据写进统一审核报告
- 对本轮全部实际差异统一做一次 code review，修复发现后复验
- 在验收完成、成果已进入显式目标分支且两端工作区干净后，按授权运行 `sync-worktree.rb`；同步验证成功后运行 `cleanup-worktree.rb` 完成本轮临时目录收口

## 不许做的

- 不改「明确不动」的项目
- 不顺手重构旁边的模块
- 不新增需求里没写的接入方式、重试或配置项
- 不把 `.env`、Nacos 示例里的密码和地址抄进文档、日志或测试快照
- 不在该系统说明里写明「不要在这里迁移」的仓库里执行迁移
- 不在任务没勾完、验收未通过或评审未完成时，把迭代标成 `done`
- 不用 `rm -rf` 或 `git worktree remove --force` 绕过脏 worktree 保护，也不自动删除成果分支
- 不替人启动前后端服务来「顺便验一下」，除非这一轮明确要求，并且人已经同意

## 收工要留下

- 任务清单里已完成的勾选
- 测试记录里的命令和手工结果
- 若接口字段有变，在该轮 `implementation-plan.md` 末尾用白话列出字段名和使用方
