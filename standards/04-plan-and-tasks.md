# 计划与任务

## 实现计划

用白话写清技术做法，不贴大段代码。至少包括：

- 数据上加什么，老数据的默认值
- 请求从页面到转发，中间哪一层做分支
- 为什么只改这一层，避免每个调用方各写一套
- 和「不做」里的路径怎样隔开

## 任务清单

一条任务只做一件事。固定写成：

`- [ ] T-01 说明。依赖：无。文件：路径。检查：一条命令`

没有检查命令的任务不算拆完。检查命令在全部任务实现完成后汇总去重执行，不在每个任务结束时重复运行。文件不在改动范围里的，不能写进任务。

建议顺序：

1. 数据和迁移
2. 校验和保存
3. 真正生效的那一处分支
4. 页面
5. 和实现直接相关的自动测试

可以并行的任务标出来。有依赖的写「先做完哪一条」。整套自动回归、手工用例和验收结果属于 `verify`，不再拆成实现任务。

完成当前任务的代码与必要测试实现后即可在任务清单打勾，并把 `status.md` 的 `current_task` 改到下一条；不在这里重复执行完整检查或 code review。首次全部任务勾选后进入统一检查和审核窗口；验收返工已有统一审核基线时，窗口只执行新任务的必跑检查和增量审核。新任务使用 `work_state: ready`；开始修改后改为 `in_progress`；受阻时改为 `blocked`。

实现计划、任务正文、风险和资源隔离全部确认后，状态仍保持 `plan / blocked`，等待用户以“计划审批通过”或含义明确的等价自然语言批准；若需求记录已有联合审批原话，则复用该证据。通过 `record-stage-approval.rb` 将用户原话、时间和当前计划摘要写入 `stage-approvals.md` 后，才能进入 `implement / ready`。普通写入授权不能代替计划审批；计划审批只允许阶段推进，“执行当前任务”授权单个任务，“完成所有任务”授权连续完成本轮实现任务和统一审核。验收与收口仍需各自明确授权；计划正文、任务依赖/文件/检查或风险变化后必须重新审批，任务完成勾选不影响摘要。
