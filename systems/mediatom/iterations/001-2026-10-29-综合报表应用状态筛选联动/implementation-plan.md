# 实现计划

## 做法

后端继续使用 `GET /app/applistForD`。控制器增加两个可选查询参数：账户编号列表、应用状态列表。不传时仍走现在的数据范围，结果包含已删除应用。

服务层按三种口径组装查询：

- 两个参数都没有：沿用登录用户的数据范围，不加状态条件。
- 只传账户：按这些账户的绑定关系查询，排除已删除，按应用编号去重，不再叠加登录用户数据范围。
- 传入状态：按所选状态过滤。状态列表为空时直接返回空列表，不能当成不传。选中已删除就包含已删除。

查询结果仍用现有应用简表。选出 `api_source`，有值时序列化成 `apiSource`。`appType` 保持现有字段。`AppMapper.java` 只改这条已批准 SQL 的参数声明，不新增其他查询。

前端综合报表把应用状态筛选移到应用筛选前面。账户筛选仍在两者之前。状态或账户变化时，综合报表只调用带当前账户和状态的 `applistForD`。一个状态都没选时清空应用下拉，不发请求。新列表返回后，仍在列表中的已选应用保留，其余取消，再按现有级联刷新广告位、流量分组和广告源，并沿用现在的自动查询。

小时报表使用同一套规则。应用状态移到应用前面。有状态就传状态，选了账户再传账户编号；一个状态都没选时清空应用下拉，不发请求。仍在新列表中的已选应用保留，其余取消，再刷新广告位、流量分组和广告源。状态变化时先等列表收口，再自动查询。

共享加载器里，小时报表预设也打开 `applistForD`。小时报表未选应用且未选账户时，广告位仍走原来的全量列表。

## 为什么这样切

参数判断放在服务层，SQL 只接收已经分好的条件。动态包的无参数调用继续走原来的服务入口。

两页的请求参数都放在各自的 `getGlobalAppList`。加载器只决定走 `applistForD`，不在小时报表再写一套接口。

T-01 保持完成。小时报表要传的状态和账户，就是 T-01 已经实现的两种参数，后端文件不用再改。T-02 恢复为未完成，因为综合报表部分已经落地，小时报表页面和加载器预设还没按同一套联动改完。

## 怎样避开「不做」

`getAppListByAdminIdList` 的 SQL 和封装不改，页面不再调用它。两页报表查询已有的 `appStsList` 结果过滤不改。不新增表，不启动服务。小时报表的日期、SDK 版本和应用版本不改。未选应用且未选账户时，小时报表广告位仍按全量列表加载。

`origin/main` 已经快进合入 `tianshuai`，前端分支 `feat-jira2785-appstatus` 已经从 `main` 建好。后续只在这两条分支上继续改，不把 `tianshuai` 合入 `main`，不 rebase，不推送。

Surefire 默认跳过测试，本轮不新增会被跳过的测试类。三种参数口径放在服务层，统一审核对照 SQL。T-01 的编译证据在代码未变时复用。T-02 完成后跑前端引用检查。验收用 TC-01 到 TC-08 和 SR-01 到 SR-03。
