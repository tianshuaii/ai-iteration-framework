# 实现计划

## 做法

不新建表，不改关联表里的数据。

新下拉仍是 `POST /trafficPlace/searchPublisherTrafficPlace`。进 SQL 之前先调用现有的供应商列表，拿到当前用户能看的供应商。没传供应商就用这批；传了就取交集。能看的范围为空，或交集为空，直接返回空列表，不查关联表。超管的供应商列表本来就是全部，取完仍按这个范围查。关键字仍是一个模糊、多个精确。已选 ID 仍精确匹配，并且也落在这个供应商范围里。

请求对象从服务接口的内部类挪到 `model/vo/traffic/PublisherTrafficPlaceSearchReqVo`。三个字段名不变。控制器和服务都改用这个类型。SQL 里已有的供应商 `IN` 不动，范围在进 SQL 前收好。

鲲鹏的列表、趋势、导出仍走原来的「不支持就返回空」。非空的 `trafficPlaceIdList` 重新算作不支持。广告位、接入类型、包名保持原来就会返回空。

鲲鹏筛选页去掉流量广告位那一项，发出的查询里不再带 `trafficPlaceIdList`。综合报表和小时报表的筛选项不改。

## 为什么这样切

供应商范围只用现有的供应商列表，不另写一套权限。查询只在新下拉这一处收口，老接口 `getTrafficPlace` 不动。

鲲鹏没有这一列，所以不能在 SQL 里加条件。恢复成「带了就返回空」，页面不再发出这个条件，避免用户看到未过滤的全量。

范围判断做成不连库的方法，测试传入两份名单，不查数据库。构建会跳过 `mvn test`，检查改用测试控制台。

## 怎样避开「不做」

- 不改老下拉接口的范围算法。
- 不改综合报表、小时报表页面。
- 不改流量广告位 ID 的原样匹配。
- 不改 `/report/fullReport` 的 `loginNum`、`payNum`。
- 不改多曝光报表和定时任务。
- 不碰本地环境文件。
- 鲲鹏搜索页已超过 300 行，只删筛选项和请求里的这个字段，不拆文件。
