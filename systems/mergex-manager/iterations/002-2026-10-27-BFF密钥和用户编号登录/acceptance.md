# 验收标准

| 编号 | 对应测试 | 标准 | 结果 |
|---|---|---|---|
| AC-01 | TC-01 | 请求只带与常量一致的 `X-BFF-Secret` 和存在且未停用的 `X-BFF-User-Id`，不带 token。需要登录的接口按这个用户返回，不报 token 失效 | 通过 |
| AC-02 | TC-02 | 两个新头都不带，只带原来的 token。校验和现在一样，通过后仍是 token 里的用户 | 通过 |
| AC-03 | TC-03 | 两个头都带了，但密钥不对。即使同时带了有效 token，也拒绝，不按 token 放行 | 通过 |
| AC-04 | TC-04 | 密钥对，但用户编号不是数字、用户不存在或用户已停用。直接拒绝 | 通过 |
| AC-05 | TC-05 | 只带 `X-BFF-Secret` 或只带 `X-BFF-User-Id`。直接拒绝，不退回 token | 通过 |
| AC-06 | TC-06 | 登录成功时 `data.token` 是登录凭证，`data.userId` 是该用户的数字编号。失败返回不改 | 通过 |
| AC-07 | TC-07 | 页面收到对象时只把 `data.token` 存成登录凭证。收到字符串时仍整段存储 | 通过 |

结果通常使用“未测”“通过”或“未通过”。只有用户明确确认接受未验证项或残余风险时，才写 `豁免：用户确认……；残余风险……`，不能只写“豁免”“收口”或把没测过的项目写成通过。
