# 需求与注意事项：BFF密钥和用户编号登录

范围见 [change-scope](./change-scope.md)。验收见 [acceptance](./acceptance.md)。当前进度只看 [status](./status.md)。

## 背景

需要登录的接口现在只认请求头里的 token。token 里带着用户编号、角色、角色类型和时区。登录成功时，`POST /user/login` 的 `data` 就是这一串 token。页面把整个 `data` 存成登录凭证。

BFF 调用时不会带 token。它会带 `X-BFF-Secret` 和 `X-BFF-User-Id`。这两个都通过时，按这个用户返回，不再做 token 校验。只带 token 时，仍走原来的 token 校验。

## 本次要做

### 页面

MergeX 登录成功后，如果 `data` 是对象，本地存储和页面里的 token 状态都只放 `data.token`。`data.userId` 不另做页面用途。如果 `data` 仍是字符串，这两处都照旧整段存储，避免另一套仍返回字符串的登录被带坏。登录页本身不改布局。

### 接口与保存

`POST /user/login` 成功时，`data` 改为对象，字段是 `token` 和 `userId`。`userId` 是这个用户的数字编号。验证码、账号、密码和停用判断保持原样。失败时的返回不改。

需要登录的接口增加一条入口：

- 请求里没有 `X-BFF-Secret`，也没有 `X-BFF-User-Id`：只走原来的 token 校验，包括原来的会话和刷新。
- 两个头都在，密钥与代码里的常量一致，用户存在且未停用：按这个用户放行。不再校验 token，也不再查登录会话。角色、角色类型和时区用这个用户自己的，和登录签发 token 时用的是同一套。
- 只带了其中一个头，或者两个头都在但密钥不对、用户编号不是数字、用户不存在、用户已停用：直接拒绝，不退回去看 token。

密钥由实现时生成一串，只放进管理端已有常量类。不写进日志、报错和本轮文档。

### 数据

不新建表，不改已有用户数据。

## 默认与老数据

| 场景 | 行为 |
|---|---|
| 只带原来的 token | 和现在一样校验，通过后仍是这个用户 |
| 已登录页面 | 登录凭证仍是 token 字符串。接口改成对象后，页面只取出其中的 token |
| 两个新头都通过 | 不要求这个用户先登录过，也不看 redis 里的登录会话 |

## 不做

- 不改验证码、密码校验和登录失败原因。
- 不改开放接口的 `x-api-key` 校验。
- 不改 Mediatom 登录页的布局和文案。
- 不改定时任务仓库。
- 不把密钥写进迭代文档、日志或报错。

## 注意事项

- 具体文件见改动范围。
- 后面的业务仍通过现有方法读取当前用户、角色和时区。入口放行后要让这些方法读到这个用户，避免把业务代码逐个改一遍。
- 大文件这轮只加这一处判断，不借机拆文件。
