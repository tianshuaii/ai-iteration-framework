# 测试用例

前置：管理端和 MergeX 页面用当前分支。准备一个未停用用户和一个已停用用户。密钥用代码常量，不写进记录。

## TC-01 两个头都通过

1. 不带 token。带上与常量一致的 `X-BFF-Secret`，以及未停用用户的 `X-BFF-User-Id`。
2. 调用一个需要登录的接口。

期望：按这个用户返回。不报 token 失效。

## TC-02 只带 token

1. 不带两个新头。
2. 只带原来的有效 token，调用同一个接口。

期望：和改之前一样通过，用户是 token 里的那个。

## TC-03 密钥不对

1. 两个头都带，密钥与常量不一致，同时带一个有效 token。
2. 调用需要登录的接口。

期望：拒绝。不按 token 放行。

## TC-04 用户不可用

1. 密钥正确。用户编号分别试非数字、不存在、已停用。
2. 调用需要登录的接口。

期望：三种都拒绝。

## TC-05 只带一个头

1. 只带 `X-BFF-Secret`，或只带 `X-BFF-User-Id`。可以同时带有效 token。
2. 调用需要登录的接口。

期望：拒绝，不退回 token。

## TC-06 登录返回

1. 用正确账号、密码和验证码登录。
2. 再用错误密码登录一次。

期望：成功时 `data.token` 有值，`data.userId` 是该用户编号。失败返回和现在一样，没有这个对象。

## TC-07 页面只存 token

1. 看登录成功后的存储。
2. 再确认如果返回仍是字符串，存储的仍是那一整段。

期望：对象时存的是 `data.token`，不是整个对象。字符串时整段存储。

## SR-01 登录后的当前用户

1. 按 TC-06 登录成功。
2. 打开当前用户信息。

期望：能拿到当前用户。停止：不测注册和改密。

## SR-02 旧 token 仍能打开列表

1. 只用原来的 token，打开一个需要登录的列表。

期望：列表能打开。停止：不测报表筛选和定时任务。
