# 实现计划

## 做法

不新建表，不改已有用户数据。

登录成功时，`POST /user/login` 不再把 `data` 直接做成 token 字符串。改成只含 `token` 和 `userId` 的小对象。`userId` 用登录查出来的用户编号。验证码、账号、密码和停用判断保持原样。失败时仍返回原来的错误，不包这个对象。

需要登录的接口仍在现有拦截器里分叉，不让每个业务自己判断：

- 两个新头都没带：后面整段 token、会话和刷新保持原样。
- 带了其中一个，或两个都带了但不通过：直接按现在「token 无效」拒绝，编号 50008。不退回去看 token，也不在报错里写密钥。
- 两个都通过：用现成的按编号查用户。停用值仍是 `S`。角色编号和角色类型用登录签发 token 时的同一套：用户自己的角色，角色上的管理员标记当作角色类型，时区用用户自己的。不再查登录会话，也不写新的登录会话。查完把这四个值放在这一次请求上。后面的当前用户、角色、角色类型和时区先读这次请求，没有再去解 token。这样业务代码不用逐个改。

密钥在写代码时生成一串，只放进 `ConstantUtil`。两个头的名字也放在那里。比对用整段字节比较，不把密钥写进日志和报错。文档里不出现这串值。

页面只改共用登录存储：`data` 是对象时，本地存储和 token 状态都只放 `data.token`；仍是字符串时整段存储。

## 为什么这样切

分支只放在拦截器和当前用户读取上。业务接口本来就从这里拿当前用户。放行后补上用户、角色和时区，后面不用知道这次是密钥还是 token。

判断本身做成不连库的方法，测试用项目里已有的测试框架，传入假用户，不查数据库。构建会跳过 `mvn test`，所以检查命令改用测试控制台跑这一类。真正查用户仍用现成的查询。

两个仓库的文件不重叠，管理端和页面可以并行。测试策略里的 T-01、T-02 已经定好，计划不再改那张表。

## 怎样避开「不做」

- 开放接口的 `x-api-key` 仍走原来的分支，不读这两个新头。
- 不改验证码、密码和登录失败原因。
- 不改 Mediatom 登录页的布局。取用户信息、退出登录不动。
- 不改定时任务仓库。
- 不碰本地环境文件：管理端的 `application.yml`，页面的开发地址。
- `user.js` 已经超过 300 行，这轮只改登录取值那两处，不拆文件。
- 另一条正在实现的轮次用的是另一套仓库，不用这两个目录。所以用真实目录，不建副本。

## 字段变化

尚未改代码。

| 字段或路径 | 谁在用 | 变化 |
|---|---|---|
| `POST /user/login` 的 `data` | 页面登录存储 | 成功时从 token 字符串改为 `token`、`userId`。失败不改 |
| `X-BFF-Secret`、`X-BFF-User-Id` | 需要登录的接口 | 两个都没带才走 token。通过则按该用户放行。不通过回 50008 |
| 当前用户、角色、角色类型、时区 | 登录后的业务 | 这次请求已放行时读查出来的用户，否则仍从 token 解 |
