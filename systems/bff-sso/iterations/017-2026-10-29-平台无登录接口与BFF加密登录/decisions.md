## 待确认事项

### Q6 加密信封与长度边界

- 问题：`RSA-OAEP-256` 直接加密 JSON 会受到 RSA 明文长度限制。是否把 `encryptedPassword` 定义为版本化混合加密信封，由 RSA 包装随机 AES 密钥，再由 AES-GCM 加密 `password + issuedAt + nonce`？
- 推荐：使用版本 `v1` 的信封，外层请求仍保持 `keyId + encryptedPassword`；`encryptedPassword` 是 Base64URL 编码的结构化信封，内部包含 RSA 加密的随机 AES-256 密钥、96 位 IV 和 AES-GCM 密文。
- 影响：协议字段数量不增加，支持任意合理密码长度并具备密文完整性校验，但前后端加解密实现比纯 RSA 多一步。
- 可复制回复：`Q6 按推荐做`

### Q7 Redis 故障与多实例一致性

- 问题：nonce 如何跨 SSO 实例原子去重？Redis 不可用时是放行登录还是拒绝登录？
- 推荐：使用 Redis `SET key value NX EX 120` 原子占位；所有 SSO 实例共享同一 nonce 命名空间和同一 Nacos 密钥环。Redis 不可用时失败关闭，返回稳定的“登录安全校验暂不可用”，不能降级为不防重放。
- 影响：Redis 故障期间用户无法登录，但不会在基础设施异常时静默降低安全等级；已有 Session 不受影响。
- 可复制回复：`Q7 按推荐做`

### Q8 公钥获取、缓存与重试

- 问题：前端从哪里拿公钥，是否缓存；轮换期间遇到未知或过期 `keyId` 时是否自动重试？
- 推荐：BFF 提供统一匿名 `GET /api/auth/login-key`，内部从 SSO 获取当前公钥；响应包含 `keyId/publicKey/algorithm/expiresAt` 并设置 `Cache-Control: no-store`。前端每次点击登录后先取公钥再加密；仅在明确的密钥过期错误时重新取钥、重新加密并自动重试一次。
- 影响：每次登录多一次轻量取钥请求，但不在浏览器长期保存公钥，轮换期间也能自动恢复；普通账号密码错误绝不自动重试。
- 可复制回复：`Q8 按推荐做`

确认依据：Q1～Q5 已由用户原话 `Q1-Q5 都按推荐做` 确认；Q6～Q8 等待用户直接回答。
