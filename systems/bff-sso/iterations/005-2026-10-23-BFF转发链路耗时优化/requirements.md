# 需求与注意事项：BFF 转发链路耗时优化

范围见 [change-scope](./change-scope.md)。待确认事项见 [decisions](./decisions.md)。验收见 [acceptance](./acceptance.md)。当前进度只看 [status](./status.md)。

## 背景

用户在 2026-10-23 的请求查询截图中看到：`GET /proxy/mergex/user/code` 的请求详情耗时 672 ms，其中从 HTTP 入站到转发 Span 开始约 653 ms；对应列表行显示 18 ms。用户反馈后端实际业务处理只用十几毫秒，希望优化 BFF 收到请求后、转发及响应前后的额外耗时。本轮是性能优化，不增加业务能力。

这张截图只证明两个口径和一段长间隔，不能证明 653 ms 都花在“读取请求体”或某个数据库查询上。列表耗时来自子请求条目，详情耗时来自整条 BFF 请求。时间轴将同一毫秒的 `http.request`、`http.body` 合并，以相邻事件间隔绘图；GET 示例没有可据此归因的请求体。详情还提示采集记录不完整，因此单个样本不能作为优化前基线。当前日志读取逻辑把缺少 `http.response` 的 Trace 标成不完整，而直通用原始响应流并单独记 `forward.response`；需要核实这是否造成误报，再区分真正的采集丢失。

当前直通代码在创建转发 Span 前，依次查生效包、加载运行包接口清单、匹配方法与路径、按白名单决定是否检查会话、查接入服务并解析目标地址；接口清单加载会读取运行包和三层 blob。哪一段实际耗时最多，需要分段测量确认。

2026-10-23 只读定位补充：从日志库取回同一接口的 4 条真实 Trace，BFF 整条请求为 600～970 ms，转发前区间为 574～792 ms，子请求段为 18～177 ms。当前数据库记录显示该接口在 HTTP 运行包的白名单里，接入方式为 `direct`；这四条请求的长区间不应归因于登录校验或 Nacos 选实例。独立脚本用仓库的开发配置重复读取同一运行包时，完整接口清单加载为 0.7～4 秒；其中 `sys_runtime_upstream_blob` 查询在一次样本里占 375/731 ms，另两次为 1137/1591 ms 与 1565/2114 ms。运行包含 328 条原接口、329 个上游 blob，读取正文约 0.55 MB，本地解析只需约 0～8 ms。这些独立读测与运行中 BFF 的 653 ms 不是同一次调用，不能做精确相减，但一致指向“每次直通都加载完整运行包文档”的热路径。

已有运行包解析器把整份约 0.5 MB 的上下文存入 Redis；独立读取该缓存 4 次为 653～1461 ms，反序列化及列接口只有数毫秒。直接换用这一份大对象缓存不能作为性能目标已达成的证据。

## 本次要做

### 页面

- 请求查询的列表与详情应清楚说明“子请求耗时”和“BFF 整条请求耗时”的口径，避免把 18 ms 与 672 ms 当成同一段时间。
- 时间轴的阶段名称要与实际测量边界一致。入站到下一事件的间隔不能简单命名为“读取请求体”；有缺口时明确显示记录不完整，不用缺失事件推断瓶颈。
- 不新增业务页面、表单或筛选条件。

### 接口与保存

- 先对同一环境、同一接口重复采样，分别测量入站、请求解析、路由前检查、运行包查找、接口清单读取与匹配、会话校验、目标地址解析、上游请求、响应传回和日志采集的耗时。记录冷/热请求、请求体大小、HTTP 方法及直连/Nacos 模式。采集不得记录密钥、Token 或业务敏感正文。
- 结合分段证据定位 BFF 自身的主要耗时，再优化对应热路径。优先核对截图所示 HTTP 直通；`POST /proxy/one` 和 `/proxy/batch` 至少作为回归与对照。若瓶颈落在范围外文件，先补改动范围再实现。
- 优化后以相同请求、环境、负载与采样方式复测 BFF 整条请求、BFF 额外耗时及上游耗时，报告 P50/P95、样本量、冷/热差异和异常样本。用户已确认：同一测试环境、同一白名单 GET 接口，预热后从 BFF HTTP 入站到发起上游请求前的耗时 P95 ≤ 100 ms。冷路径另报实测值，不用热路径目标掩盖首个请求。
- 保留原有直通路径的方法/接口匹配、唯一生效包、白名单与登录校验、原始流式转发和不设转发超时的语义；`/proxy/one` 与 `/proxy/batch` 的登录、信封和超时行为保持原样。
- 请求日志仍不得影响业务结果；采集失败和不完整记录需要可见且不能被计入可信性能基线。

### 数据

- 不增加治理表字段或迁移。若实测表明必须改变数据结构，需要先回到规格阶段取得明确确认。
- 现有接口项目、运行包、生效包、会话和白名单数据保持原义。任何缓存方案都必须说明失效事件、最长陈旧时间与权限/路由变更的正确性，不能仅用提高命中率换取过期权限或旧包转发。

## 默认与老数据

| 场景 | 行为 |
|---|---|
| 既有 HTTP 直通请求 | 路径、鉴权、上游请求和流式响应语义不变；只减少已定位的 BFF 额外耗时。 |
| 既有单发、批量请求 | 保持协议和响应契约；纳入性能对照与功能回归。 |
| 既有请求日志 | 历史数据按原字段读取；缺失或不完整样本不被误当作可靠基线。 |

## 不做

- 不增加新的业务接口、权限规则或页面功能。
- 不修改上游服务的业务实现，也不把上游处理时间冒充 BFF 耗时。
- 不擅自关闭会话校验、接口匹配、日志脱敏或失败记录以换取耗时下降。
- 不执行数据库迁移、服务重启或部署。

## 注意事项

- 文件范围以 [change-scope](./change-scope.md) 为准。产品仓库有历史未提交改动，进入实现前必须逐文件记录并隔离。
- 性能结论只适用于实际测过的环境、版本和负载。截图是问题线索，不是重复采样的基线。
