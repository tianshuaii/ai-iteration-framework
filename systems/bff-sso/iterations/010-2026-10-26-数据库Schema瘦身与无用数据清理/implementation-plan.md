# 实现计划

## 做法

本轮以 `adx-admin-backend` 为 `public_management` 的唯一结构变更来源。先在其 Prisma Schema 和注释清单中删除已确认不再保留的模型、`sys_sub_service.service_kind` 字段及关联枚举/索引声明；再新增一份前向迁移。迁移先锁定并校验目标 Schema、迁移元数据、4 个有效服务、4 个有效接口项目及每个服务/环境的 active/previous 运行包保留集合，任何前提不满足即 `RAISE EXCEPTION` 停止。

迁移通过显式依赖顺序清除已删除服务、已删除接口项目、所有保留表中的 `yn=0` 记录、28 个未引用的有效标记历史运行包，以及其独占的 Item 与 Blob；共享 Blob 只有在不存在任何保留引用时才删除。随后删除 23 张已有无引用证据的历史表和 `service_kind` 字段。不得使用宽泛 `CASCADE`，不得按表名猜测删除对象。

`adx-bff-backend` 与 `adx-sso-backend` 仅同步 Prisma 模型及实际受影响的定向测试；尤其移除 SSO 中已与真实 Schema 脱节的旧服务字段。它们不执行 `prisma migrate deploy`，以避免历史迁移链触碰共享库。

实际库操作采用两段门禁：先生成逻辑全量备份、SHA-256 和前置清单，恢复至独立临时库后完成只读不变量核验；获得单独迁移执行授权后，停止五项本机服务对线上测试库的写入并在 `adx-admin-backend` 执行唯一迁移。迁移后重新生成清单、运行定向回归；失败时停止并通过已验证备份恢复，而不是运行伪回滚 SQL。

## 为什么这样切

- 数据删除、DDL 和备份/恢复边界集中在唯一迁移源，避免三套后端各自迁移共享 Schema。
- 保留集由运行激活关系和有效项目关系计算，先校验再删除，避免仅依赖 `yn` 或包时间猜测。
- BFF、SSO 只同步生成模型和受影响查询，保持本轮在真实调用点的最小改动。
- 实际迁移与代码实现分开：计划审批和代码实施不等同于线上测试库写入授权。

## 怎样避开「不做」

- 不改两个前端；页面只是自然不再展示已物理删除的数据。
- 不改有效服务的接口、鉴权或交互，也不清理 `sys_audit_log`。
- 不触碰 `public_management` 之外的 Schema、生产库或两个迁移元数据表。
- 无法在迁移前置检查中证明无引用的对象保持不删，并写入残余清单。

## 执行顺序与恢复

1. 实现前记录三个真实仓库的逐文件 dirty 基线；不覆盖 009 未提交成果。
2. 完成迁移、模型同步与定向测试代码，统一 code review 并修复。
3. 取得独立的迁移/服务操作授权后，执行备份、恢复演练、前置清单与唯一迁移。
4. 用迁移后清单和定向回归验证；任何步骤失败即停止，恢复动作只使用已演练的备份流程。

## 字段变化

开始时尚未改产品代码；下表是已批准计划，不是已执行结果。

| 字段或路径 | 谁在用 | 变化 |
|---|---|---|
| `public_management.sys_sub_service.service_kind` | 无当前 Prisma/源码/数据库依赖引用；现存 7 行均为历史上游数据。 | 在唯一迁移中删除列，并从三后端模型中移除对应声明。 |
| 23 张已确认历史表 | 无当前五仓源码、Prisma 或数据库依赖引用。 | 在前置无引用检查通过后显式删除；保留 `_prisma_migrations` 与 `flyway_schema_history`。 |
| `sys_sub_service_runtime_package` 及依赖 | 有效服务只需要 active/previous；其余失效或未引用历史包无运行引用。 | 删除 `yn=0` 包和 28 个未引用历史包；保留集合不满足即停止。 |
| `sys_interface_*` 已删除项目链路 | 30 个项目为 `yn=0`；4 个有效项目要保留完整历史。 | 只删除失效项目及其依赖和无引用 Blob。 |
