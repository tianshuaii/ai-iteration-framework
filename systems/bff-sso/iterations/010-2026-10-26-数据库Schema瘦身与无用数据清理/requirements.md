# 需求与注意事项：数据库 Schema 瘦身与无用数据清理

范围见 [change-scope](./change-scope.md)。验收见 [acceptance](./acceptance.md)。当前进度只看 [status](./status.md)。

## 背景

上一轮已将 Admin 治理能力收口到账户，但线上测试环境 `public_management` 仍保留历史服务、接口项目、运行包、动态表单和基础字典等旧结构与数据。当前只读盘点发现 57 张表，其中 30 个接口项目、3 个服务、8 条运行激活、147 个运行包及其他多类记录处于 `yn=0`；还存在未被当前三个后端 Prisma 模型覆盖的历史表。

本轮目标是以当前实际运行能力为边界，删除已经失效且不再被使用的表、字段和数据，减少历史包袱，同时保证当前四个有效服务、接口编辑、BFF 转发、SSO 登录与 Admin 账户管理不受影响。

## 本次要做

### 页面

- 不新增页面功能。
- 若清理后现有管理页展示的数据范围变化，只允许删除已经失效的服务、项目和历史包记录，不改变有效记录的字段语义与操作入口。

### 接口与保存

- 保留当前有效服务对应的接口编辑、运行包激活、回滚和转发能力。
- 被物理删除的服务、接口项目和运行包不得再被列表、详情、激活或转发接口查询到。
- 数据库结构变化必须同步到实际访问 `public_management` 的 Prisma 模型；迁移只允许由 `adx-admin-backend` 承载。

### 数据

- 物理删除所有表中的 `yn=0` 数据，并按外键和业务引用顺序删除其依赖记录。
- 物理删除已经删除的服务，以及这些服务关联的运行激活、历史运行包、包内条目和失去引用的 Blob。
- 物理删除已经删除的接口项目，以及关联分支、提交、工作区、Tree Item、白名单、合并记录、接口包记录和失去引用的 Blob。
- 删除经当前源码、数据库依赖和运行能力三方证明确实未使用的表。
- 删除经当前源码、数据库依赖和运行能力三方证明确实未使用的字段；当前已确认的候选字段是 `sys_sub_service.service_kind`。
- 实际执行前必须形成删除清单、行数清单和可恢复备份；执行后重新生成同口径清单并核对差异。

## 默认与老数据

| 场景 | 行为 |
|---|---|
| 新建 | 本轮不新增业务数据；迁移后的新数据继续遵循现有模型和 `yn` 约定。 |
| 已有有效数据 | 保留当前有效服务、有效接口项目及其仍被运行链路使用的数据。 |
| `yn=0` 数据 | 作为本轮明确例外，物理删除，不再保留软删除墓碑。 |
| 删除服务和项目的依赖数据 | 按引用关系一并物理删除，并清理仅由这些记录引用的 Blob。 |
| 无法证明未使用的表或字段 | 默认保留，列入残余清单，不凭名称或空表直接删除。 |

## 不做

- 不清理 `public_management` 之外的数据库或 Schema。
- 不改变当前有效服务的业务接口、鉴权规则或前端交互。
- 不在需求阶段执行迁移、删除或部署。
- 不把没有证据的“看起来没用”当成删除依据。

## 注意事项

- 文件列表见改动范围，这里不重复贴路径。
- 本轮物理删除是用户对通用软删除习惯的明确单轮例外，不改变后续业务删除仍使用软删除的默认规则。
- 目标环境、有效数据保留口径、历史包保留口径和审计数据处置已由 D-04 至 D-09 固化。
