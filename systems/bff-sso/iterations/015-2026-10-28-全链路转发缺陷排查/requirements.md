# 需求与注意事项：全链路转发缺陷排查

范围见 [change-scope](./change-scope.md)。验收见 [acceptance](./acceptance.md)。当前进度只看 [status](./status.md)。

## 背景

`mergex-manager` 系统的 002「BFF密钥和用户编号登录」已经做完：管理端认 `X-BFF-Secret` 和 `X-BFF-User-Id`，两个头都对才按用户放行，不再看调用方 token；只带 token 时仍走原校验。

BFF 这边，HTTP 直通在非白名单时会注入这两个头，**不会**把调用方的 BFF token 转给子服务。两边契约要对上，全链路才能通。本轮按这条链路排查转发缺陷，并只修落在 `bff-sso` 的问题。

## 本次要做

### 排查与归类

1. 对照 `mergex-manager` 002 的约定，核对「调用方 → BFF HTTP 直通 → MergeX 管理端」。
2. 四种状态都要查：
   - **登录前**：还没拿到 BFF Session 时，白名单、开放接口、误打到需登录接口各自怎么转。
   - **登录时**：平台登录接口免 Session、上游响应接管、返回给调用方的形态。
   - **登录后**：非白名单带平台上下文时，密钥和用户编号怎么注入、是否误带 token。
   - **登录失效**：Session 过期、被清掉或校验失败时，是否还往下游塞身份头，调用方看到什么。
3. 每条缺陷标明责任侧：`bff-sso` 或 `mergex-manager`（含其页面仓库）。
4. 起查方式：先按 002 契约做只读四段审计；若有具体失败请求，优先当第一案。

### 修复边界

- 落在 `bff-sso` 五仓之内的缺陷：直接纳入本轮改动并修。
- 落在 `mergex-manager` 系统的缺陷：本轮**不改**那边代码；责任侧确认后马上在 `mergex-manager` 系统新开一轮承接，不必等本轮全部查完。本轮只留下问题清单和指向。

### 页面 / 接口 / 数据

本轮不预设必须改页面。接口字段默认不新增；若审计发现必须改 BFF 发出的头或登录接管形态，再在计划里落到具体文件。不新建表，不动治理迁移，除非审计证明库表就是断点（当前不预期）。

## 默认与老数据

| 场景 | 行为 |
|---|---|
| 白名单 HTTP 直通 | 仍不要求 BFF Session，也不注入平台密钥和用户编号 |
| 非白名单 HTTP 直通（有效平台 Session） | 仍只注入服务端可信的密钥和用户编号，不转发调用方 BFF token |
| 登录失效 / 未登录打需登录接口 | 拦在 BFF，不带着假身份打到上游 |
| 只带 token 直连管理端 | 仍由管理端按原 token 校验，不属于 BFF 注入路径 |

## 不做

- 不在本轮直接改 `mergex-manager` / `mediatom-web` / `mergex-datasyn`。
- 不借排查扩大到 gRPC `/proxy/one`、账号权限后台或无关功能，除非审计证明断点在那里。
- 不把平台请求密钥写进迭代文档、日志或报错原文。

## 注意事项

- 对口对照：`systems/mergex-manager/iterations/002-2026-10-27-BFF密钥和用户编号登录/`。
- 密钥值两边各自保管；排查只核对“是否一致、是否发出”，不把明文写进本轮文档。
- 具体改哪些 BFF 文件，等缺陷定位后再写进改动范围和任务。
