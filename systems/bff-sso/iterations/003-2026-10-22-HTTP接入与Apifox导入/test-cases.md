# 测试用例

前置：网关管理页能登录。示例 Apifox 项目 ID 只用占位，例如 `7654321`。不要把真实项目 ID、令牌或内网地址写进记录。

## TC-01 新建 HTTP 接口项目只保存

1. 打开「接口项目」，点新建。
2. 不填原接口 Apifox 项目 ID，直接保存。
3. 填上 ID，再保存。

期望：

- 接口类型默认是 HTTP，这一项有必填星。不填不能保存。
- 第二次保存成功。
- 这次没有向 Apifox 拉取，原接口文档仍是空的。
- 列表能看到 HTTP 和这个 ID。

## TC-02 新建 gRPC 项目仍导入 Proto

1. 新建接口项目，类型改成 gRPC。
2. 不填原接口 Apifox 项目 ID，保存。
3. 打开该项目的原接口文档，点导入。

期望：

- 不要求原接口 Apifox 项目 ID。Proto URL 可以不填。
- 按钮仍是「导入 Proto」，弹窗仍要 Proto 地址。
- 列表里来源项目显示 `-`。

## TC-03 导入接口并先看差异

1. 用 TC-01 建好的 HTTP 项目，先导入一次，推送到分支。
2. 让来源项目里的接口相对这一版有新增、修改、删除。
3. 在「原接口文档」和「项目分支」各点一次「导入接口」。

期望：

- 两个按钮都叫「导入接口」，都不要求再填地址。
- 能看到新增、修改、删除。
- 还没确认时，已有改造和整合不变。
- 确认后，这两层才按差异更新。

## TC-04 失败和只改资料都不拉取

1. 把 Apifox 令牌配成无效，或让导出失败，再点「导入接口」。
2. 恢复令牌。编辑该 HTTP 项目，只改名称，或只改原接口 Apifox 项目 ID，保存。

期望：

- 导出失败时提示失败，工作区里的原接口还是上一次的。
- 只改名称或 ID 的保存成功，但不出现新的拉取结果。

## TC-05 老接口项目仍是 gRPC

1. 打开迁移前就有的接口项目，点编辑。
2. 试图把类型改成 HTTP。
3. 回到原接口文档点导入。

期望：

- 类型显示 gRPC，不能改。
- 按钮仍是「导入 Proto」。

## TC-06 新建接入服务默认 HTTP

1. 打开「接入服务」，点新建。
2. 看通信方式和 Apifox 相关输入。
3. 不填原来的推送用 Apifox 项目 ID，保存。

期望：

- 通信方式默认 HTTP。
- 页面上没有「原接口 Apifox 项目 ID」。
- 原来的 Apifox 项目 ID 仍可空，说明仍是推送运行包。
- 保存成功。

## TC-07 HTTP 转发不用 gRPC 端口

1. 把一条已有接入服务改成 HTTP，直连地址用文档示例 `192.0.2.10:8080`。
2. 用一包 HTTP 接口调用 `/proxy/one`，方法和路径都填。
3. 再把同一条改成 Nacos，实例没有 `httpPort`，再调用一次。

期望：

- 直连打到 `http://192.0.2.10:8080`，不出现 `grpc://`。
- 没有 `httpPort` 的那次失败，不改用实例的 gRPC 端口。
- 连通测试弹窗写成 HTTP，不写成 gRPC 探测。

## TC-08 gRPC 老路径还在

1. 不修改一条仍是 gRPC 的接入服务，按原来的方式转发一次。
2. 打开平台内建 SSO 的编辑弹窗。

期望：

- 转发仍不接受 method，仍走 gRPC。
- SSO 的通信方式不能改。

## TC-09 推送运行包仍用接入服务上的 ID

1. 接口项目上的原接口项目 ID 填 `7654321`。
2. 接入服务上的推送用 Apifox 项目 ID 填另一个值。
3. 在「服务接口包」对正在使用的包点「推 Apifox」。

期望：

- 推送目标是接入服务上的那个 ID。
- 不是接口项目上的 `7654321`。
