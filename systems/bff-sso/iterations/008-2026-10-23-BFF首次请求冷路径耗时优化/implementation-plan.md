# 实现计划：BFF 首次请求冷路径

## 做法

1. 保留已审批的四条路径、固定本机替身上游及“`/health` 就绪后第一条业务请求”口径。先在 BFF 内补脱敏、单调钟分段：直通的运行包查询、清单读取/匹配、会话、服务和目标解析；单发/批量的守卫、Session 读取/续期/上下文刷新、运行包解析、上游与批量聚合。并发批量的分段使用各自局部起点，不能让共享 `lastNs` 互相覆盖。事件只记录阶段与耗时，不记录 Token、正文和目标地址。
2. 直通冷匹配当前调用 `getInventory`，会读取包及上游、门面、组合三层 blob，再从完整结果提取方法与路径。把直通专用的路由集合读取下沉到 `RuntimePackageInventoryService`：只验证包归属及有效性并读取构造原接口集合所需的上游文档；保留 `getInventory` 管理用途不变。`HttpPassthroughService` 继续以运行包主键做同包并发合并、失败后删除缓存、切包时清理旧键；缺失或损坏时拒绝转发，不以空清单或旧清单放行。
3. 单发/批量仍经 `ProxyService` 的共同解析入口，不改变两条 API。对默认生效包，若分段确认整份 Redis 物化正文读取/解析是重复主因，则在 `RuntimeInterfaceResolver` 中复用进程内已验证上下文，并由 `RuntimeInterfaceCacheSyncService` 提供每请求可核验的轻量生效包版本。版本与正文的写入、删除需保持一致；不一致、缺失或 Redis 不可用时重新从权威来源确认，不得凭旧进程快照放行。激活、回滚、归档及跨实例事件要使旧上下文失效。显式 `packageId` 仍走原有 manifest 校验，不借默认包缓存绕过环境或状态检查。若实测主因不是大对象，先记录证据并调整计划重新审批，不盲目引入缓存。
4. 如果分段显示守卫前置间隔仍是主组瓶颈，只在 `session.guard.ts`、`session.service.ts` 或账号上下文客户端做有证据的安全等价优化；Session 刷新组单独报告，不通过跳过账号状态、续期或授权上下文刷新来压低主组。无需改动时保持这些文件不变。
5. 在本轮 `scripts/` 留下可重复的脱敏采样入口：分别重启 BFF、等 `/health`、只发该路径一条业务请求，标记异步预热、浏览器预检、Session 刷新和版本；固定上游、样本筛选及 P50/P95/极值算法可复核。先在优化前为四路各留至少 30 个有效独立重启样本，避免拿既有 3 次探索值计算基线 P95；优化后正式每路再取至少 30 个有效样本，并做完整安全/热路径回归。两组共至少 240 次独立重启，分受控短窗口执行，开始前再次核对本机运行资源与临时直连恢复办法；正式结果属于 `verify`，不能只凭脚本存在宣布达标。

## 为什么这样切

- 直通冷匹配与单发/批量运行时解析是两条不同路径；在各自共同入口优化，避免调用方分散缓存或页面特殊处理。
- 第 008 轮定位只能确认直通整包读取及单发/批量大对象读取是候选瓶颈；先留分段证据再实施对应优化，不把整段等待武断归给数据库或 Redis。
- 本轮不增表、不迁移，也不改变旧数据默认值；旧包、旧会话仍按现有生效包、白名单、登录及显式选包规则处理。

## 怎样避开「不做」

- 不改两个管理页、SSO、账号后端、前端接口和响应口径；不新增业务接口、权限或迁移。
- 不清 Redis、不切运行包、不对真实业务服务加压；固定上游的临时改址按已批准的本机范围执行并在同轮读回原值。
- 不以异步预热完成作为 `/health` 之外的额外等待条件；若主组目标不能安全达成，保留实测结果并回规格/计划请用户确认，不自行放宽阈值。

## 字段变化

尚未改代码。计划中只增 BFF 内部脱敏计时阶段和缓存内部版本标识；HTTP 路径、请求/响应字段及日志对外字段契约不变。若实施时需要改变对外字段或新增持久数据，先返工规格并重审。

| 字段或路径 | 谁在用 | 变化 |
|---|---|---|
| `GET /proxy/<publicPath>/<originalPath>` | 直通调用方 | URL、鉴权、原接口判定、响应不变。 |
| `POST /proxy/one`、`POST /proxy/batch` | 单发及批量调用方 | 请求与响应信封、`requestId` 对应、单项失败隔离不变。 |
| BFF 内部计时阶段、运行时缓存版本 | 诊断和缓存同步 | 仅内部增加；不改变页面耗时显示口径或数据库结构。 |
